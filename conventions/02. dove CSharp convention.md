## 1. 들어가며

- 이 문서는 작성자 dove의 C# 컨벤션을 정리한 것이다.
- 이 문서는 C#에 적용되는 공통 규칙과 C# 전용 규칙, 적용 예시를 함께 담는다. C# 작업에 필요한 기준을 이 문서에서 이어서 읽을 수 있다.
- 공개 API와 라이브러리 설계는 Microsoft의 [Framework Design Guidelines](https://learn.microsoft.com/ko-kr/dotnet/standard/design-guidelines/)를, 일반적인 코드 스타일은 [Common C# code conventions](https://learn.microsoft.com/ko-kr/dotnet/csharp/fundamentals/coding-style/coding-conventions)를 기본 토대로 삼는다.
- 여기서 다루지 않은 서식 사항은 [Microsoft C# 서식 가이드라인](https://learn.microsoft.com/ko-kr/dotnet/fundamentals/code-analysis/style-rules/csharp-formatting-options)을 따르는 것을 기본 원칙으로 한다.

### 1-1. 적용 기준

- 적용 우선순위는 프로젝트 지침·설정 → C# 컨벤션 → 공통 컨벤션이다.
- 공통 규칙은 [공통 코드 컨벤션](02.%20dove%20common%20convention.md)의 내용을 같은 `COM` ID로 이 문서에도 수록한 것이다. 공통 규칙을 변경할 때는 같은 ID를 가진 항목을 함께 갱신한다.

### 1-2. 규칙 강도

| 강도 | 의미 |
|---|---|
| Must | 반드시 준수한다. |
| Should | 특별한 이유가 없다면 준수한다. |
| May | 상황과 의도에 따라 선택할 수 있다. |
| Must Not | 사용하지 않는다. |
| Should Not | 특별한 이유가 없다면 사용하지 않는다. |

### 1-3. 규칙 표기

- 규칙은 `ID`, `강도`, `규칙` 열을 가진 표로 작성한다.
- ID는 `범위-분류-번호` 형식이다. 예: `CS-WRAP-03`
- 범위는 공통 규칙이 `COM`, C# 전용 규칙이 `CS`이다. 이 문서에 수록한 공통 규칙은 공통 코드 컨벤션과 같은 `COM` ID를 사용한다.
- 규칙에 딸린 짧은 설명과 예시는 같은 칸에 적는다. 코드 예시는 표 아래에 두고, 어떤 규칙의 예시인지 ID로 밝힌다.
- 한 번 부여한 ID는 규칙의 위치가 바뀌어도 유지하고, 삭제한 규칙의 ID는 재사용하지 않는다. 새 규칙에는 같은 분류의 마지막 번호 다음 번호를 붙인다.

## 2. 코드 컨벤션

### 2-1. 명명 컨벤션

#### 2-1-1. 기준

식별자 이름은 해당 요소의 핵심 역할이 바로 드러나도록 짓는다.

#### 2-1-2. 기본 명명 규칙

##### 2-1-2.1. 구체적인 이름 사용

| ID | 강도 | 규칙 |
|---|---|---|
| COM-NAME-01 | Should | 숫자나 모호한 이름보다, 의미가 드러나는 구체적인 이름을 우선한다. |

##### 2-1-2.2. 언더스코어 사용

| ID | 강도 | 규칙 |
|---|---|---|
| CS-NAME-01 | Should | 기본적인 PascalCase / camelCase만으로 의미 전달이 어려울 때만 제한적으로 `_`를 사용한다. 예: `TestDisposedDisconnectSegmentNotContaining` 대신 `Test_Disposed_DisconnectSegment_NotContaining` |
| CS-NAME-02 | Must Not | 공개 API에서는 `_`를 사용하지 않는다. 공개 API에서는 더 짧고 명확한 이름, 혹은 네임스페이스 계층으로 의미를 분리한다. |

#### 2-1-3. 한정자 사용 규칙

| ID | 강도 | 규칙 |
|---|---|---|
| CS-MOD-01 | Should | private 필드나 메서드에 `private` 한정자를 사용한다. |
| CS-MOD-02 | Should | `sealed` 한정자를 남용하지 않는다. 상속을 강하게 제한할 필요가 있을 때만 `sealed` 한정자를 사용한다. |
| CS-MOD-03 | Should | 변경되지 않는 구조체의 경우 `readonly` 한정자를 사용한다. |

#### 2-1-4. 식별자별 명명 규칙

##### 2-1-4.1. private 필드

| ID | 강도 | 규칙 |
|---|---|---|
| CS-NAME-03 | Must | `const`를 제외한 모든 private 필드는 `_` 접두사를 사용한다. |
| CS-NAME-04 | Should Not | `s_`, `t_` 같은 별도 접두사는 사용하지 않는다. |

##### 2-1-4.2. 소스 코드 파일 / 폴더 / 어셈블리

| ID | 강도 | 규칙 |
|---|---|---|
| CS-NAME-05 | Must | PascalCase를 사용한다. 단, `src`, `samples`, `tests`, `docs`처럼 저장소 구조를 나타내는 최상위 디렉터리는 [네이밍](../instructions/네이밍.md)의 저장소 이름 기준에 따라 소문자로 쓸 수 있다. |
| CS-NAME-06 | Must | 폴더 경로의 물리적 계층은 `/`로, 어셈블리 등 논리적 이름의 계층은 `.`으로 표현한다. 예: `UniEngine/Plugins/GeoSystem.Tests` |
| CS-NAME-07 | Must Not | 공백은 사용하지 않는다. |

##### 2-1-4.3. 상수

| ID | 강도 | 규칙 |
|---|---|---|
| CS-NAME-08 | Must | `const`는 PascalCase를 사용한다. |
| CS-NAME-09 | Must Not | `const`나 `readonly`에 `SCREAMING_SNAKE_CASE`를 쓰지 않는다. |

##### 2-1-4.4. 열거형

| ID | 강도 | 규칙 |
|---|---|---|
| CS-NAME-10 | Must | 일반 enum 형식명은 단수형, `[Flags]` enum 형식명은 복수형으로 작성한다. |
| CS-NAME-11 | Must | enum 형식이나 식별자에 `Enum`, `Flags` 같은 접미사는 붙이지 않는다. |
| CS-NAME-12 | Should | enum임을 드러내야 할 때는 의미 중심 이름을 쓰고, 정말 필요할 때만 `Type`, `Kind`, `Mode`, `State` 등을 붙인다. |

### 2-2. 구조 컨벤션

#### 2-2-1. 영역 구분 규칙

| ID | 강도 | 규칙 |
|---|---|---|
| COM-REGION-01 | Should | 멤버를 역할별로 묶고 영어 주석으로 영역을 구분한다. |
| COM-REGION-02 | Should | 하위 묶음은 멤버 이름만으로 역할을 구분하기 어렵거나, 영역이 길어 한 화면(약 60줄)에서 구성이 한눈에 들어오지 않을 때만 나눈다. |
| COM-REGION-03 | May | 코드가 짧으면 영역 구분 주석을 생략할 수 있다. |
| COM-REGION-04 | Should | 영역은 `Front`, `Property`, `Internal`, `Content`를 기본 틀로 삼아 이 순서로 배치하고, 해당 멤버가 없는 영역은 생략한다. |
| COM-REGION-05 | Should | 하위 묶음이 둘 이상인 영역은 영역 주석 뒤에 공백 한 칸과 `-` 20개를 붙이고, 그 아래의 하위 묶음은 구분선 없는 영어 주석으로 구분한다. |

기본 틀의 각 영역은 아래 멤버를 담는다.

| 영역 | 의미 |
|---|---|
| `Front` | 공개 멤버 |
| `Property` | 도메인 객체가 사용하지 않는 공개 멤버 |
| `Internal` | private 필드 |
| `Content` | 생성자와 메서드 |

하위 묶음 이름은 `Construction`, `Connections`처럼 묶음에 담긴 기능이 드러나게 짓는다. 하위 묶음이 하나뿐이면 나누지 않고 영역 주석만 둔다.

아래 예시는 하위 묶음 표기를 보여주기 위해 줄인 것으로, 실제로는 `Content`가 한 화면을 넘을 만큼 길 때 이렇게 나눈다. `Content`는 하위 묶음이 셋이므로 구분선을 붙이고(`COM-REGION-05`), `Front`와 `Internal`은 하위 묶음 없이 영역 주석만 둔다.

```csharp
public class Connection
{
    // Front
    public bool IsOpen { get; private set; }

    // Internal
    private readonly string _address;


    // Content --------------------
    // Construction
    public Connection(string address) => _address = address;

    // Connections
    public void Open() => IsOpen = true;
    public void Close() => IsOpen = false;

    // Regular
    public override string ToString() => _address;
}
```

#### 2-2-2. 빈 줄 규칙

| ID | 강도 | 규칙 |
|---|---|---|
| COM-BLANK-01 | Should | 일반적인 논리적 묶음이나 영역 사이는 빈 줄 한 줄로 구분한다. |
| COM-BLANK-02 | Should | 멤버 선언 영역과 `Content` 영역 사이는 빈 줄 두 줄로 구분한다. |
| COM-BLANK-03 | May | 코드가 짧으면 멤버 선언 영역과 `Content` 영역 사이를 빈 줄 한 줄로 구분할 수 있다. |
| COM-BLANK-04 | May | 밀접하게 연관된 멤버, 오버로드, 단축 메서드 등 같은 역할을 하는 메서드는 빈 줄 없이 이어서 작성할 수 있다. |

멤버 선언 영역과 `Content` 영역 사이의 간격은 해당 영역 구성을 사용하는 경우에 적용한다.

아래 예시에서는 `ValueChanged`를 도메인 객체가 사용하지 않고 외부 관찰자가 구독하는 공개 멤버로 가정한다. 멤버 선언 영역과 `Content` 영역 사이는 빈 줄 두 줄로 구분하고(`COM-BLANK-02`), 같은 역할을 하는 `Add` 오버로드는 빈 줄 없이 이어서 작성한다(`COM-BLANK-04`).

```csharp
using System;

public class Counter
{
    // Front
    public int Value => _value;

    // Property
    public event Action<int> ValueChanged;

    // Internal
    private int _value;


    // Content
    public Counter(int value) => _value = value;

    public void Add() => Add(1);
    public void Add(int value)
    {
        _value += value;
        ValueChanged?.Invoke(_value);
    }
}
```

#### 2-2-3. 코드 블록 규칙

##### 2-2-3.1. 한 줄 코드 블록

| ID | 강도 | 규칙 |
|---|---|---|
| CS-BLOCK-01 | Should | 한 줄짜리 블록은 식 본문 멤버를 우선 사용한다. |
| CS-BLOCK-02 | May | 필요하면 한 줄 중괄호 블록도 허용한다. |
| CS-BLOCK-03 | Should Not | 세 문장 이상을 한 줄에 몰아넣지 않는다. |

```csharp
// CS-BLOCK-01
private void Start() => DoSomething();
```

```csharp
// CS-BLOCK-02
private void Start() { DoSomething(); }
```

##### 2-2-3.2. 두 줄 이상 코드 블록

| ID | 강도 | 규칙 |
|---|---|---|
| CS-BLOCK-04 | Should | 두 줄 이상 블록은 Allman(BSD) 스타일을 사용한다. |
| CS-BLOCK-05 | Must Not | 두 줄 이상 블록에서 다른 스타일은 사용하지 않는다. |

```csharp
// CS-BLOCK-04
private void Start()
{
    DoSomething();
}
```

##### 2-2-3.3. 한 줄 빈 코드 블록

| ID | 강도 | 규칙 |
|---|---|---|
| CS-BLOCK-06 | Should | 한 줄 빈 블록은 `{ }` 형태로 작성하고, 중괄호 사이에 공백 한 칸을 둔다. |
| CS-BLOCK-07 | May | 여러 줄 선언문에 딸린 블록은 가독성상 다음 줄에 `{ }`를 둘 수 있다. 단, 짧고 단순한 선언은 그 방식으로 쓰지 않는다. |

```csharp
// CS-BLOCK-06

```

##### 2-2-3.4. 두 줄 빈 블록

| ID | 강도 | 규칙 |
|---|---|---|
| CS-BLOCK-08 | Should | 두 줄 빈 블록은 빈 줄 없는 Allman(BSD) 스타일로 작성한다. |
| CS-BLOCK-09 | Should Not | 중간에 빈 줄을 넣지 않는다. |

#### 2-2-4. 줄바꿈 규칙

##### 2-2-4.1. 기준

- 콤마는 항상 **이전 요소의 끝**에 둔다.
- 같은 수준의 인자는 같은 레벨로 보이게 정렬한다.
- 호출 구조는 공간을 아끼는 방향으로, 자료구조 표현은 구조가 드러나는 방향으로 줄바꿈한다.

##### 2-2-4.2. 연산자 줄바꿈

| ID | 강도 | 규칙 |
|---|---|---|
| CS-WRAP-01 | Should | 연산자는 다음 줄 첫 항목 앞에 둔다. |
| CS-WRAP-02 | May | 문자열 결합처럼 가독성이 더 중요한 경우에는 가장 읽기 좋은 위치로 조정할 수 있다. |

```csharp
// CS-WRAP-01
if (value >= predicate
    && !isRunning)
```

```csharp
// CS-WRAP-01
private readonly Exception _animationFailure
    = new InvalidOperationException("애니메이션 재생 중 오류가 발생했습니다.");
```

##### 2-2-4.3. 인자 목록 줄바꿈

| ID | 강도 | 규칙 |
|---|---|---|
| CS-WRAP-03 | Should | 긴 인자 목록이나 제네릭 목록은 여러 줄로 나눌 수 있다. 첫 줄 일부를 유지하고 다음 줄부터 한 번 들여쓰거나, 첫 줄부터 바로 개행하고 각 인자를 한 줄씩 배치한다. |
| CS-WRAP-04 | Should Not | 닫는 괄호 `)` 또는 `>`를 별도 줄에 두지 않는다. |
| CS-WRAP-05 | May | 깊은 메서드 체이닝이나 중첩 자료구조에서는 가독성을 위해 닫는 괄호를 다음 줄로 내릴 수 있다. |
| CS-WRAP-06 | Must Not | 콤마를 새 줄 첫머리에 두지 않는다. |

|---|---|---|

| CS-WRAP-08 | Should | 본문이 없는 `record`는 자료구조처럼 개행할 수 있다. |

```csharp
// CS-WRAP-07

}
```

```csharp
// CS-WRAP-08
public record PlayInfo
(
```

##### 2-2-4.5. 람다 표현식과 식 본문 멤버

| ID | 강도 | 규칙 |
|---|---|---|
| CS-WRAP-09 | Should | 람다와 식 본문 멤버는 선언부의 일부로 보고 같은 흐름 안에서 배치한다. 중괄호가 없다면, 마치 중괄호가 있었을 때의 들여쓰기 감각을 유지한다. |

```csharp
// CS-WRAP-09

```

###### 2-2-4.5.1. 람다/식 본문 멤버의 switch 식

| ID | 강도 | 규칙 |
|---|---|---|
| CS-WRAP-10 | Should | switch 식은 보통 줄바꿈 후 본문처럼 배치한다. |
| CS-WRAP-11 | May | 짧고 단순한 경우에는 메서드와 같은 줄에 `=> value switch` 형태로 둘 수 있다. |

```csharp
// CS-WRAP-10
private string ToString(SettingInfo info) =>
    info.Type switch
    {
        MyEnum.None => "None",
        MyEnum.Normal => "Normal",
        MyEnum.Special => "Special",
        _ => throw new ArgumentOutOfRangeException(nameof(info.Type), info.Type, null)
    };
```

##### 2-2-4.6. 상속 및 구현 줄바꿈

| ID | 강도 | 규칙 |
|---|---|---|
| CS-WRAP-12 | Should | 상속/구현 목록이 길면 줄바꿈을 사용할 수 있다. 콤마는 이전 줄 끝에 두고, 두 번째 줄부터는 한 번 들여쓰며, `:` 위치는 가독성과 의도가 가장 잘 드러나는 방식으로 배치한다. |
| CS-WRAP-13 | Must Not | 콤마를 다음 요소 앞에 두지 않는다. |
| CS-WRAP-14 | Must Not | `:` 앞뒤를 붙여 쓰지 않는다. |
| CS-WRAP-15 | Must | 생성자 이니셜라이저의 `: base(...)`는 다음 줄 시작에 둔다. |
| CS-WRAP-16 | Should | 제네릭 제약은 `where` 절 단위로 줄바꿈할 수 있다. |

#### 2-2-5. 메서드 배치 규칙

| ID | 강도 | 규칙 |
|---|---|---|
| COM-ORDER-01 | Should | 메서드는 가능한 한 생애주기 순서로 배치한다. |
| COM-ORDER-02 | Should | 같은 생애주기 단계에서는 논리적으로 관련된 기능끼리 묶어 배치한다. |
| COM-ORDER-03 | Should | 각 기능 묶음 안에서는 사용 흐름에 따라 배치한다. |

생애주기 순서는 생성·사용·정리 단계가 있는 대상에 적용한다. 배치 기준은 다음과 같이 큰 흐름에서 세부 흐름으로 적용한다.

1. **생애주기 순서**: 생성자 → 일반 메서드 → `Dispose`·소멸자 순서로 배치한다.
2. **논리 순서**: 같은 생애주기 단계의 메서드를 관련 기능별로 묶어 배치한다. 예: 노드 관리 → 세그먼트 관리.
3. **사용 흐름**: 각 기능 묶음 안에서 기능을 사용하는 일반적인 절차에 따라 배치한다. 예: 등록 → 조회 → 삭제.

예를 들어 노드와 세그먼트를 관리하는 객체는 일반 메서드를 기능과 사용 흐름에 따라 묶어 다음과 같이 배치할 수 있다.

```text
생성자
노드 관리: 등록 → 조회 → 삭제
세그먼트 관리: 등록 → 조회 → 삭제
Dispose·소멸자
```
