# dove’s Documentation Convention

## 목차

1. 문서화 구조
2. 개요 문서 구조
3. 구현 문서 구조
4. 기타

## 1. 문서화 구조

### 1-1. 의도

문서화는 해당 코드의 정체성, 즉 '이 코드는 무엇인가'를 한 문장으로 정의하는 작업이다. 이를 통해 코드가 해결하고자 하는 문제의 범위와 역할을 명확히 하고, 그 목적을 달성하기 위해 어떤 방식으로 구현할 것인지에 대한 아이디어를 공유한다.

이 과정은 참여자가 기능의 본질을 이해하도록 돕는다. 참여자가 단순한 코더나 API 사용자를 넘어, 설계 의도를 이해하고 능동적으로 생태계에 참여하기 위해서는 이러한 이해가 필수적이다.

### 1-2. 구조

문서는 기본적으로 아래와 같은 구조를 따른다.

1. **개요 문서**

   코드의 정체성을 소개하는 문서이다.
   기능의 개요, 목적, 구현 방향을 간단히 제시하여 참여자가 전체적인 감을 잡을 수 있도록 한다.

2. **구현 문서**

   코드의 구체적인 구현 가이드라인을 소개하는 문서이다.
   개요 문서에서 제시한 목적을 실제로 달성하기 위해 어떤 구조가 필요한지 설명함으로써, 참여자가 각 코드의 역할과 상호작용을 이해할 수 있도록 한다.

다만 코드의 의도와 규모에 따라 문서의 종류와 내용은 달라질 수 있다. 예를 들어, 간단한 도구 문서의 경우 구현 문서가 생략될 수 있으며, 복잡한 구조를 가진 프레임워크의 경우 다단계의 개요 문서와 구현 문서로 구성될 수도 있다. 또한 필요에 따라 논문, API 문서, 코드 스니펫 문서 등 추가 문서가 포함될 수 있다.

## 2. 개요 문서 구조

개요 문서는 코드의 정체성과 독자가 처음 잡아야 할 큰 그림을 소개하는 문서이다. 개요 문서의 기준은 독자가 '이 기능은 무엇을 해결하는가', '어떤 구조로 문제를 해결하는가', '어떤 흐름으로 동작하는가'를 먼저 이해할 수 있게 하는 데 있다.

개요 문서는 주로 아래와 같은 구조를 따른다.

1. **목차**

2. **소개**

   기능이 필요한 상황이나 기존 방식의 한계, 기능의 개요, 목적, 구현 방향을 각각 한 문장 수준으로 간결하게 제시한다.
   프레임워크나 도구 문서에서는 `개요`, `목적`, `구현`을 제시하는 것을 기본으로 한다. 개념 문서나 원칙 문서처럼 표보다 문장 목록이 자연스러운 경우에는 핵심 내용을 bullet로 제시할 수 있다.

이후에는 기능을 단계적으로 소개하여, 사용자가 해당 기능의 전체 구조와 의도를 자연스럽게 이해할 수 있도록 구성한다.
개요 문서의 본문은 아래와 같은 독자 이해 순서를 기본으로 한다.

1. **기능의 정의와 목적**
   앞에서 제시한 문제를 이 기능이 어떤 관점에서 해결하는지 설명한다.

2. **해결 방향 또는 구현 방향**
   세부 구현을 나열하기보다 문제를 해결하는 큰 전략을 설명한다.

3. **핵심 구조와 대표 흐름**
   주요 구성 단위, 기본 동작 흐름, 기능 간의 의존 관계를 큰 단위로 설명한다.

4. **확장 기능, 선택지, 출력 결과**
   기본 기능 위에 추가되는 기능이나 사용자가 선택할 수 있는 정책, 최종적으로 얻는 결과를 설명한다.

다만 모든 문서가 위 항목을 같은 분량으로 가질 필요는 없다. 간단한 기능은 일부 항목을 합쳐 짧게 설명할 수 있으며, 복잡한 프레임워크는 문제 영역별로 본문을 나누어 설명할 수 있다.

또한 개요 문서는 아래와 같은 밀도와 흐름으로 작성하는 것을 기본으로 한다.

- 첫 문단에서 기능을 한 문장으로 정의한다.
- 초반에는 `개요`, `목적`, `구현`처럼 문서 전체를 짧게 요약하는 축을 제시한다.
- 그 다음에는 기능의 특징이나 핵심 성질을 짧게 묶어 소개한다.
- 이후 본문에서는 주요 구조, 대표적인 사용 방식, 또는 문제 영역별 구성을 큰 단위로 나누어 설명한다.
- 기능을 병렬 목록으로만 나열하지 않고, 가능한 한 기본 기능에서 확장 기능으로 이어지는 의존 순서에 따라 설명한다.

즉 개요 문서는 세부 API를 설명하는 문서가 아니라, 독자가 먼저 '이 프레임워크는 무엇을 해결하는가', '어떤 큰 구조를 가지는가', '어떤 방식으로 동작하는가'를 파악할 수 있도록 작성하는 것이 중요하다.

좋은 개요 문서는 구성 요소를 모두 세세하게 해설하기보다, 시스템의 큰 분류와 대표 흐름을 먼저 보여주고, 각 부분이 왜 필요한지 이해할 수 있을 정도까지만 안내한다.

사용 예시나 코드 스니펫은 개요 이해에 필요한 최소한만 포함한다. 구체적인 사용 절차, 메서드 선택 기준, 튜토리얼성 코드는 별도의 Usage 문서나 API 문서로 분리하는 것을 기본으로 한다.

## 3. 구현 문서 구조

구현 문서는 일반적으로 목차로 시작한다. 이후 개발자가 개요 문서의 아이디어를 코드 구조로 구체화할 수 있도록, 아래와 같은 요소를 필요에 따라 포함한다.

- 시스템의 구성 요소
- 구성 요소 간의 관계를 나타내는 다이어그램
- 개요 문서에서 소개한 기능의 구현 방식
- 코드 스니펫
- 구현 시 고려해야 할 규칙이나 제약

구현 문서는 단순히 코드를 설명하는 문서가 아니라, 기능의 목적을 실제 구조와 흐름으로 연결하는 가이드라인 문서로 구성되어야 한다.

단, 구현 문서는 가이드라인을 제공하는 문서이므로 모든 세부 구현 사항을 포함하지 않을 수 있으며, 특정한 코드 형태를 보장하지 않는다. 구현 문서는 세부 사항에 함몰되어 전체 흐름을 가리기보다, 구현의 방향과 기준을 제시하는 역할에 충실해야 한다.

또한 구현 문서의 밀도는 각 API나 메서드를 빠짐없이 나열하는 수준보다 한 단계 위에서 잡는 것을 기본으로 한다. 좋은 구현 문서는 구성 요소가 무엇인지, 각 구성 요소가 어떤 책임을 가지는지, 그리고 이들이 어떤 순서와 흐름으로 동작하는지가 먼저 보이도록 작성한다.

즉 구현 문서는 API 문서처럼 세세한 호출 목록을 전부 적기보다, 아래와 같은 수준을 우선한다.

- 시스템의 주요 구성 요소와 그 역할
- 구성 요소별 대표 동작 방식
- 전체 실행 파이프라인 또는 단계별 흐름
- 확장 방식이나 결합 방식의 차이
- 구현 시 반드시 알아야 하는 규칙과 제약

필요하다면 예시 코드나 세부 함수명을 일부 포함할 수 있으나, 그것이 문서의 중심이 되어서는 안 된다. 구현 문서를 읽었을 때 독자가 '무슨 클래스가 있나'보다 '이 프레임워크가 어떤 단위로 나뉘고 어떻게 흘러가는가'를 먼저 이해할 수 있어야 한다.

구현 문서의 본문은 아래와 같은 흐름을 기본으로 한다.

1. **전체 구조**
   구현을 이루는 주요 구성 요소와 관계를 먼저 보여준다. 필요한 경우 다이어그램이나 구성 요소 목록을 사용한다.

2. **핵심 구성 요소**
   각 구성 요소가 어떤 책임을 가지며, 어떤 정보를 보유하고, 어떤 서비스를 제공하는지 설명한다.

3. **대표 실행 파이프라인**
   실제 동작이 어떤 순서로 흘러가는지 단계별로 설명한다. 이때 호출 순서, 상태 변화, 객체 간 연결 방향이 드러나야 한다.

4. **구조적 의도와 설계 기준**
   왜 이러한 분리가 필요한지, 어떤 문제를 피하기 위한 구조인지 설명한다.

5. **구현 시 고려사항**
   생명주기, 스레드 안전성, 확장 정책, 종료 조건, 예외 처리처럼 구현자가 반드시 알아야 하는 제약을 정리한다.

구현 문서는 사용법 문서와 구분한다. 특정 메서드를 어떤 상황에서 호출해야 하는지, 가장 짧은 사용 흐름이 무엇인지, 튜토리얼을 따라 코드를 작성하는 방법은 Usage 문서에 가깝다. 구현 문서에 코드 예시가 들어가더라도, 그 예시는 사용자를 안내하기 위한 예제가 아니라 구조와 흐름을 설명하기 위한 보조 자료여야 한다.

구현 문서에서 파일 목록이나 API 목록을 제공할 수는 있으나, 그것이 문서의 중심 구조가 되어서는 안 된다. 파일 목록은 구현 구조를 모두 설명한 뒤 보조 색인으로 배치하는 것이 적절하다.

### 3-1. 객체 구현 문서

객체를 소개하는 구현 문서의 경우, 아래의 항목을 기본 구조로 삼는다.

- 객체의 역할(책임)
- 객체가 가지고 있는 정보(필드와 프로퍼티)
- 객체가 제공하는 서비스(API)와 제공 이유

이 항목은 자유 산문으로 길게 늘어놓기보다, 독자가 빠르게 비교할 수 있도록 짧은 문장이나 `항목: 설명` 형식으로 정리하는 것을 기본으로 한다. 객체 설명 이후에는 객체들이 함께 작동하는 대표 흐름을 별도로 제시하여, 개별 객체 설명이 전체 실행 흐름과 연결되도록 한다.

## 4. 기타

- 문체는 `~이다` 체를 사용한다.
- 인용부호를 사용할 때는 작은따옴표(`'`)를 사용한다.
- 제목에는 인용부호나 백틱을 사용하지 않는 것을 기본으로 한다. 본문에서도 인용이나 기술적 표현의 구분이 필요한 경우에만 제한적으로 사용한다. 이는 편집 용이성과 문서 간 일관성을 보장하기 위한 규칙이다.
  - `Func<bool>`과 같이 마크다운 문법(`<`, `>` 등)과 충돌하는 경우에는 백틱을 사용할 수 있다.
