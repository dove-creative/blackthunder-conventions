# 네이밍

## 목적

이 문서는 저장소 이름, 패키지 식별자, 네임스페이스, 빌드 산출물 이름, 표시 이름처럼 같은 개념을 서로 다른 위치에 적을 때 어떤 표기 방식을 사용할지 정리한다.

이름은 사용되는 표면에 따라 역할이 다르다. 배포 시스템이 읽는 식별자는 외부 생태계의 규칙을 우선하고, 코드에서 드러나는 식별자는 해당 언어의 API 관례와 컨벤션을 우선한다.

특정 언어나 플랫폼에만 존재하는 개념과 구체적인 표기는 언어별 문서에서 다룬다. C#과 .NET 프로젝트는 [네이밍 - C#](네이밍%20-%20CSharp.md)을 함께 따른다.

## 기본 원칙

- 같은 대상을 가리키더라도 패키지 식별자와 코드 식별자는 같은 대소문자를 강제하지 않는다.
- 설치, 배포, 경로, 레지스트리 식별자는 해당 생태계의 관례를 우선한다.
- 네임스페이스나 모듈 경로처럼 코드에서 읽히는 식별자는 해당 언어의 컨벤션을 우선한다.
- 사용자가 보는 표시 이름은 식별자 규칙보다 읽기 쉬운 자연어 표기를 우선한다.

## 저장소 이름

Git 저장소 이름은 URL, 클론 폴더, 서브모듈 경로에 사용되는 식별자이므로 소문자와 하이픈(`-`)으로 작성한다. 프로젝트 이름이 PascalCase여도 저장소 이름은 소문자로 쓴다.

예:

```text
프로젝트: BlackThunder.UniEngine
저장소: blackthunder-uniengine
```

저장소를 클론한 최상위 폴더는 저장소 이름을 따르고, 그 안의 프로젝트 폴더와 파일은 해당 언어의 컨벤션을 따른다.

단, `src`, `samples`, `tests`, `docs`처럼 저장소의 구조를 나타내는 최상위 디렉터리는 저장소 이름과 같은 Git 경로 표기의 일관성을 위해 소문자로 쓸 수 있다. 이 디렉터리 아래의 프로젝트 폴더와 파일은 다시 해당 언어의 컨벤션을 따른다.

예:

```text
blackthunder-uniengine/
├─ src/
│  └─ BlackThunder.UniEngine/
├─ samples/
└─ tests/
   └─ BlackThunder.UniEngine.Tests/
```

## 패키지 식별자

패키지 식별자는 설치, 배포, 패키지 해석에 사용되는 이름이다. 다른 패키지와 충돌하지 않도록 소유자명부터 시작하고, 동일한 제품군은 공통 접두사를 사용한다.

패키지 식별자는 패키지의 소유자와 제품을 안정적으로 나타내도록 작성한다. 소유자명과 제품명을 구분하는 방식과 대소문자는 배포 생태계의 규칙을 따른다.

## 네임스페이스

네임스페이스나 외부에서 참조하는 모듈 경로는 코드 API의 일부이므로 회사명 또는 소유자명에서 시작한다.

같은 런타임 소스를 여러 프로젝트에서 공유하는 경우에도 네임스페이스는 동일하게 유지한다. 사용 환경에 따라 네임스페이스가 달라지면 샘플, 테스트, 문서의 참조 구문이 갈라지고 공개 API가 불안정해진다.

## 빌드 산출물 이름

빌드 산출물 이름은 산출물의 주된 목적이 드러나도록 작성한다.

테스트, 샘플, 도구처럼 하위 산출물이 필요하면 대표 산출물 이름 뒤에 하위 구성을 나타내는 세그먼트를 붙인다. 프로젝트 파일명도 산출물 이름과 맞추는 것을 기본으로 한다.

## 표시 이름

사용자가 보는 이름은 식별자보다 읽기 쉬운 표기를 우선한다. 패키지 제목, 샘플 이름, 문서 제목은 공백과 약어를 자연스럽게 사용할 수 있다.

예:

```text
UniEngine
Native C# Usage
```

## 혼동 방지

아래처럼 표면을 섞지 않는다.

- 패키지 식별자나 산출물 이름에 `BlackThunder UniEngine`처럼 공백을 사용하지 않는다.
- 한 표면의 표기를 다른 표면에 그대로 옮겨 쓰지 않는다. 예를 들어 소문자만 쓰는 패키지 식별자를 네임스페이스에 그대로 사용하지 않는다.
- 표시 이름이 필요한 곳에는 `BlackThunder.UniEngine` 같은 코드 식별자보다 `UniEngine`처럼 읽기 쉬운 이름을 사용한다.
