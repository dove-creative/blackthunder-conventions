## 1. 개요

### 1-1. 목적

이 문서는 저장소나 패키지의 루트 README를 어떤 기준으로 작성할지 정리한다.

README는 사용자가 저장소나 패키지를 처음 열었을 때 가장 먼저 만나는 공개 문서이다. 따라서 README는 모든 문서를 대신하기보다, 대상이 무엇이고 어떻게 시작할 수 있으며 자세한 내용은 어디에서 읽을 수 있는지를 짧고 안정적으로 안내해야 한다.

특정 언어나 플랫폼에만 해당하는 명령과 코드 예시는 언어별 문서에서 다룬다. C#과 .NET 프로젝트는 [README 템플릿 - C#](README%20템플릿%20-%20CSharp.md)을 함께 따른다.

### 1-2. README의 역할

README는 저장소나 패키지의 첫 화면 문서이다.

좋은 README는 사용자가 아래 질문에 빠르게 답할 수 있게 한다.

- 이 저장소나 패키지는 무엇인가
- 기존 방식과 비교했을 때 어떤 문제를 해결하는가
- 어떤 기능을 제공하는가
- 어떤 환경이 필요하고 어떻게 설치하거나 실행하는가
- 가장 작은 사용 예시는 무엇인가
- 주요 API는 어떤 표면을 가지는가
- 자세한 문서, 테스트 방법, 라이선스는 어디에 있는가

README는 구현 세부 사항을 모두 설명하는 문서가 아니다. 세부 구조와 사용 기준은 Overview, Implementations, Usage, API 문서로 넘기고, README에는 사용자가 첫 실행까지 도달하는 데 필요한 최소한의 정보만 둔다.

### 1-3. 기본 원칙

- 첫 문단에서 대상을 한 문장으로 정의한다.
- 필요한 경우 두 번째 문단에서 일반적인 방식이나 독자가 이미 아는 개념과 비교하여 대상의 관점을 분명히 한다.
- 미리보기 이미지가 있으면 초반부에 배치하여 결과물을 먼저 보여준다.
- 기능 목록은 내부 구현이 아니라 사용자가 얻는 능력 중심으로 작성한다.
- 설치와 실행은 실제로 지원하는 배포 방식과 사용 환경에 맞춰 나눈다.
- 설정값, 환경 변수, 런타임 스위치처럼 오해하기 쉬운 항목은 실제 코드 동작에 맞춰 정확히 설명한다.
- 빠른 시작 코드는 하나의 대표 흐름을 보여주는 최소 예제로 둔다.
- API 목록은 전체 레퍼런스가 아니라 README에서 알아야 할 공개 표면 요약으로 둔다.
- 자세한 설명은 저장소 안의 관련 문서로 연결한다.
- 절 제목은 사용자가 찾는 행동이나 정보 단위로 짓는다.
- README 안에서 같은 내용을 반복하지 않는다.
- 문체는 기본적으로 `~이다` 체를 사용하되, 사용자에게 직접 협조를 요청하거나 감사 인사를 전하는 짧은 문단은 자연스러운 존댓말을 사용할 수 있다.

### 1-4. 기본 구성

README는 아래 순서를 기본으로 한다.

1. 제목
2. 다른 언어 README 링크
3. 한 문장 정의와 필요한 비교 설명
4. 미리보기 이미지
5. 시작하기 전에
6. 주요 기능
7. 요구 사항과 설치
8. 빠른 시작
9. 주요 API
10. 문서
11. 테스트
12. 라이선스

대상의 성격에 따라 일부 절은 생략할 수 있다. 다만 정의, 주요 기능, 설치 또는 실행 준비, 빠른 시작, 문서 링크, 라이선스는 가능한 한 유지한다.

### 1-5. 파일 언어와 작성 순서

문서가 단일 언어라면 `README.md`를 사용할 수 있다.

둘 이상의 언어 README를 함께 제공하는 경우에도 대표 언어 문서는 `README.md`처럼 언어 코드를 생략할 수 있다. 대표 언어가 영어라면 아래처럼 작성한다.

예:

```text
README.md
README.ko.md
```

대표 언어를 포함한 모든 문서의 언어를 명시하려면 `README.en.md`, `README.ko.md`처럼 각 파일에 언어 코드를 붙인다. 대표 언어를 정하지 않는 경우에는 `README.md`를 각 언어 문서로 연결하는 짧은 진입 문서로 사용할 수 있다.

같은 언어의 전체 내용을 `README.md`와 언어 코드가 붙은 파일에 중복해서 관리하지 않는다.

한국어와 영어 README를 함께 작성할 때는 먼저 `README.ko.md`에서 구조, 설명 순서, 예시, 링크 대상을 확정한 뒤 [번역 지침](번역.md)에 따라 영어 문서를 작성하는 것을 기본으로 한다. 영어가 대표 언어라면 `README.md`로, 언어를 명시한다면 `README.en.md`로 작성한다. 폴더에 `TranslationGuide.md`가 있다면 해당 지침을 우선한다.

## 2. 소개 절

### 2-1. 제목과 언어 링크

제목은 사용자가 보는 표시 이름을 사용한다.

예:

```markdown
# Product Name
```

둘 이상의 언어 README를 제공한다면 H1 제목 바로 아래에 다른 언어 문서로 이동하는 상대 링크를 둔다. 두 문서에서 링크의 위치와 순서를 동일하게 유지한다.

영어가 대표 언어인 경우의 예:

```markdown
[한국어](README.ko.md)
```

한국어 README에서는 대표 영어 문서로 연결한다.

```markdown
[English](README.md)
```

모든 언어를 명시한다면 실제 파일명에 맞춰 `README.en.md`, `README.ko.md`를 연결한다. 언어 선택용 `README.md`를 둔다면 대상의 이름과 한 문장 설명, 제공하는 언어 링크만 간결하게 제시한다.

### 2-2. 첫 설명

첫 문단은 저장소나 패키지를 한 문장으로 정의한다.

예:

```markdown
Product Name은 사용자가 특정 문제를 일관된 방식으로 해결할 수 있도록 지원하는 라이브러리이다.
```

필요한 경우 두 번째 문단에서 익숙한 개념과 비교하여 이 대상이 문제를 바라보는 관점이나 고유한 차이를 설명한다.

이 부분에서는 구현 클래스나 세부 API를 먼저 나열하지 않는다. 사용자가 대상의 정체성을 먼저 이해할 수 있게 한다.

### 2-3. 미리보기 이미지

결과물이 눈에 보이는 저장소나 패키지는 첫 설명 다음에 미리보기 이미지를 둔다.

예:

```html
<img src="docs/images/preview.png" alt="Product Name preview" width="900">
```

미리보기 이미지는 실제 출력물, 실제 화면, 실제 사용 결과를 보여주는 것이 좋다. 장식용 이미지나 추상적인 분위기 이미지는 README의 정보 밀도를 낮추므로 피한다.

### 2-4. 시작하기 전에

프로젝트 성격, 피드백 경로, 감사 인사를 짧게 전할 필요가 있으면 `시작하기 전에` 절을 둔다.

이 절은 마케팅 문구가 아니라 사용자와의 관계를 여는 짧은 안내이다. 프로젝트가 어떤 생태계에 속하는지, 불편한 점을 어디로 알려 주면 되는지, 사용에 대한 감사를 간결하게 적는다.

이 절이 길어지면 README의 시작 속도가 느려지므로 2-3문단 안에서 끝낸다.

### 2-5. 주요 기능

주요 기능은 bullet 목록으로 작성한다.

각 항목은 기능 이름과 사용자가 얻는 결과를 함께 적는다.

예:

```markdown
- 대표 기능: 사용자가 어떤 작업을 더 쉽게 수행할 수 있게 한다.
- 결과 출력: 처리 결과를 확인하고 다음 작업에 활용할 수 있게 한다.
```

목록은 내부 파일 구조보다 사용자가 호출하거나 확인할 수 있는 능력 중심으로 둔다. 너무 많은 항목을 넣어야 한다면 별도 문서로 분리하고 README에는 대표 기능만 남긴다.

## 3. 시작 절

### 3-1. 설치

설치 절은 대상이 실제로 지원하는 방식만 안내한다.

패키지로 배포한다면 패키지 관리자의 추가 명령을 먼저 제시하고, 필요한 경우 프로젝트 설정 파일에 직접 추가하는 형식도 함께 제시한다.

저장소 자체를 빌드하거나 실행해야 한다면 필요한 SDK 버전과 명령을 별도로 적는다.

구체적인 명령과 설정 형식은 언어별 문서의 예시를 따른다.

각 설치 방식에는 사용자가 실제로 따라 할 수 있는 명령, 경로, 설정을 둔다. 배포되지 않은 방식이나 내부 개발 절차를 일반 사용자용 설치 방법처럼 안내하지 않는다.

오해하기 쉬운 설정은 설치 절에서 바로 설명한다. 설정 설명은 문서만 보고 추측하지 않고, 실제 코드와 프로젝트 설정을 확인한 뒤 작성한다.

### 3-2. 빠른 시작

빠른 시작은 사용자가 가장 작은 성공 사례를 볼 수 있게 하는 절이다.

기본 사용 코드는 대상의 핵심 사용 흐름을 하나로 보여준다. 모든 API를 넣으려 하지 말고, 사용자가 시작점을 만들고 대표 동작을 실행한 뒤 결과를 확인하는 흐름만 선택한다.

빠른 시작 절은 대표 흐름을 보여주는 코드 블록과, 코드가 수행하는 작업을 설명하는 짧은 목록으로 구성한다. 코드 예시는 언어별 문서를 따른다.

예:

````markdown
## 빠른 시작

```text
(대표 흐름을 보여주는 최소 코드)
```

이 코드는 아래 작업을 수행한다.

- 대표 서비스를 생성한다.
- 기본 동작을 실행한다.
- 처리 결과를 반환한다.
````

실행 가능한 예시 프로젝트를 제공한다면 대화형 실행과 대표 명령의 일회 실행 방법을 함께 안내한다. 예시 프로젝트의 구성과 실행 방식은 [예시 프로젝트](예시%20프로젝트.md)를 따른다.

샘플 실행 안내에는 실제 프로젝트 경로, 명령, 주요 출력 위치를 포함한다.

## 4. 참조 절

### 4-1. 주요 API

주요 API 절은 공개 표면의 빠른 색인이다.

각 항목은 `API: 역할` 형식으로 짧게 적는다.

예:

```markdown
- `ProductService`: 기능을 사용하는 대표 진입점이다.
- `Run(...)`: 대표 작업을 실행하고 결과를 반환한다.
```

API 목록은 사용자가 README만 보고 전체 구조를 대략 파악할 수 있을 정도로 제한한다. 매개변수 조합, 예외 조건, 세부 정책은 Usage 문서나 API 문서로 넘긴다.

### 4-2. 문서

문서 절에는 저장소 안의 자세한 문서로 이동하는 상대 링크를 둔다.

예:

```markdown
- [Overview](docs/Overview.md): 대상의 목적과 큰 흐름
- [Usage](docs/Usage.md): 사용 예시와 호출 기준
- [API](docs/API.md): 공개 API 상세 설명
```

문서 링크 설명은 한 줄로 끝낸다. 각 문서의 내용을 README에서 다시 설명하지 않는다. 여러 언어 문서를 제공한다면 현재 README의 언어와 같은 문서를 먼저 연결한다.

### 4-3. 테스트

테스트 절에는 테스트 실행 명령과 필요한 조건을 짧게 적는다. 구체적인 명령은 언어별 문서의 예시를 따른다.

특정 SDK, 환경 변수, 외부 서비스처럼 테스트 실행에 필요한 조건이 있으면 함께 명시한다. README에서 테스트 전략 전체를 설명하지 않는다.

### 4-4. 라이선스

라이선스 절은 라이선스 이름과 파일 링크만 적는다.

예:

```markdown
이 프로젝트는 MIT 라이선스로 배포된다. 자세한 내용은 [LICENSE.md](LICENSE.md)를 참고한다.
```

## 5. 검증 기준

README를 새로 작성하거나 수정할 때는 아래를 확인한다. 아래 항목은 대표 검증 기준이며, 대상의 성격에 따라 필요하면 앞 절의 기준을 바탕으로 추가 검증을 진행한다.

- 첫 문단이 대상을 한 문장으로 정의하는가
- 주요 기능과 주요 API가 사용자 관점의 공개 표면 요약으로 충분한가
- 설치와 빠른 시작이 실제로 지원하는 방식과 가장 작은 대표 흐름만 안내하는가
- 설정값, 환경 변수, 런타임 스위치 설명이 실제 코드와 일치하는가
- 문서에 적힌 명령, 경로, 출력 위치가 실제 프로젝트 구성과 맞는가
- 문서, 라이선스, 이미지 링크가 실제 상대 경로와 맞는가
- 여러 언어 README의 파일명, 상호 링크, 구조 대응이 1-5, 2-1과 번역 지침을 따르는가
